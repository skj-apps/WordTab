## 2. THE NEW DEFECT — the chrome sampler is the most expensive thing on the timer

The QPC bracket added in `181223c` came back from the field for the first time. On 2026-09-11 the
sampler was taking **4.1% of Word's UI thread, all day**, against 0.2-0.9% for the dot poll the whole
five-rung ladder was built for — while `strip.cpp:6747`'s comment still calls it *"the cheaper of
the two"*.

### The log contains its own A/B. Same session, same three windows, same build.

`g_strips` is ATTACH order (`strip.cpp:7147`, append on attach). The sampler walks it in index
order. The window that can answer is the z-top one — usually the most recently opened, i.e. usually
LAST. So cost = (index of the answering strip) × one sample.

```
09-08 12:43:47.408  stack active -> 0x519A4   (index 2, last-attached)
                    chrome sample means: 30811, 47031, 47387
09-08 13:35:46.091  stack active -> 0x31124   (index 0, FIRST-attached)
                    chrome sample means: 15664, 15306, 15434, 14897, 15233
```

**3x the cost purely from which tab was in front.** Nothing else changed.

Cross-check — mean / row size is stable at ~8.7k-12.9k us per window sampled:

```
09-09 row 2 -> ~29,000      09-11 row 5 -> ~44,000 (thirteen consecutive 480-pass lines)
09-09 row 4 -> ~40-52,000   09-11 row 7 -> ~62,000-82,874 (worst 214,286)
control: 09-11 16:30:55 mean 12,944 at row 6, Word in front and ANSWERING = one sample
control: minimised -> `480 passes, mean 0 us, worst 4 us` (the loop skips iconic/hidden)
```

### Three defects underneath it, in fix order

1. **The expensive readback runs BEFORE the cheap test that decides whether any of it is usable.**
   `GetDC(NULL)` `strip.cpp:1031`, `CreateCompatibleDC` `:1069`, the CAPTUREBLT blit `:1081` — and
   only then, at `:1121`, does `total < 12` discover all 24 points were foreign. The project's own
   `tools\pixel-cost.cpp` numbers are already in the comment: 24× `WindowFromPoint` is
   **79-1336 us, free**; 24× `GetPixel` was 929,092-1,284,716 us.
   **THIS IS CHANGE 1.** ~15 lines in one function. Count ownership first; if `24 - foreign < 12`,
   return the existing `"something is covering Word's ribbon"` BEFORE `:1031`; blit only the band
   you are going to read; KEEP the post-blit `total < 12` so `"too few readable pixels"` survives.
2. **`front` is `GetForegroundWindow()` (`strip.cpp:6825`)** — the oracle this project has already
   measured is not "the window in front". `stack.cpp:1286` `FrontMostJoined` already holds the right
   one (a `GetTopWindow` walk). A SEPARATE, LATER change.
3. **The stage has no governor at all** — a hard `countdown = 4` and the measured microseconds feed
   nothing but two log lines. A SEPARATE, LATER change.

## 3. WHY THE DPI BRACKET IS NOT IN THIS BUILD

The obvious fix is to bracket `strip.cpp:5351`'s `CreateWindowExW` with
`SetThreadDpiAwarenessContext(GetWindowDpiAwarenessContext(frame))` — **the frame's own handle, not
a named constant**, because the decode collapses PER_MONITOR_AWARE V1 and V2 and naming the wrong
one would create a THIRD context instead of removing a mismatch. Reached by `GetProcAddress` exactly
as `GetDpiForWindow` already is (`strip.cpp:556-565` is the shape to copy). Restore on EVERY exit
path including the `CreateWindowExW` failure branch.

**But we do not yet know that is the right fix**, and the log cannot say:

> **Every `thread-ctx` ever printed in the field was sampled INSIDE a Word window procedure**
> (`strip.cpp:1497-1498` from `_WwF`'s subclass, `frames.cpp:406` from the frame's), where Windows
> has ALREADY swapped the thread to that window's context. `CreateWindowExW` runs outside one. The
> log has never once sampled the AMBIENT context, which is the only moment that matters.

Two possibilities, and change 2 tells them apart in one report:

- thread is **system** at creation → the bracket fixes it, one line
- thread is **per-monitor** at creation and Windows downgraded the child anyway → the bracket does
  nothing and it is a different fix (hosting behaviour, or not a child at all)

**Scope, when it is time: it is ONE site, not four.**

- the coordinator (`frames.cpp:1045`) is `HWND_MESSAGE` — no pixels, no rect, nothing to mismatch.
- the tip (`strip.cpp:4592`) and ghost (`strip.cpp:3252`) are **`WS_POPUP` OWNED by the frame, not
  children** (`strip.cpp:4587` says so). Bracketing them is a separate change with a separate
  argument; it must not ride in as "minimal".

**CORRECTED, do not act on the old version:** an earlier draft said `tools\WordLayout.cs:65`'s
`SetProcessDPIAware()` makes 14 suites system-aware and should be fixed first. **It is a NO-OP** —
`check-all.ps1` runs every suite under `pwsh` 7, which already declares per-monitor-v2 in its
manifest, and the failure is swallowed by `| Out-Null`. The harness is per-monitor aware. Not an
action item; just a dead line that reads as if it does something.

## 4. EVERYTHING ELSE THE REPORT SHOWED, ranked, none of it in this build
